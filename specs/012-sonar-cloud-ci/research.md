# Research: Configure SonarCloud Analysis in CI

**Feature**: 012-sonar-cloud-ci  
**Date**: 2026-11-20  
**Status**: Complete — all design decisions resolved

## Decision: SonarCloud Scanner invocation method

**Decision**:

- The CI workflow adds a SonarCloud scan step after the "Run quality gates" step, so `coverage/lcov.info` is available before scanning.
- The scan invokes the SonarCloud Scanner via the official SonarSource GitHub Action (`sonarsource/sonarcloud-github-action`), which downloads and runs the scanner without adding an npm dependency.
- `sonar.token` is sourced from a repository secret variable (`${{ secrets.SONAR_TOKEN }}`), never hardcoded.
- `sonar.projectKey` and `sonar.organization` use placeholders in `sonar-project.properties`.
- `sonar-project.properties` lives at the repository root and references `coverage/lcov.info` for `sonar.typescript.lcov.reportPaths`.

**Rationale**: Directly implements the user's constraints — scan step after coverage, token from secret var, placeholders for project/org, no new npm dependencies (Simplicity/YAGNI), lcov report generated by vitest.

**Alternatives considered**:

- Install the SonarScanner CLI via npm (`sonar-scanner`) — rejected: adds a new dependency and version-pinning burden; the GitHub Action handles scanner download/lifecycle automatically.
- Run the scanner through a custom script — rejected: duplicates scanner orchestration logic and violates Simplicity/YAGNI.

## Decision: lcov reporter addition

**Decision**:

- `vitest.config.mts` coverage `reporter` array gains `lcov` alongside existing `text`, `json`, `html`.
- Coverage `include` (`src/**/*.ts`) and `exclude` patterns are unchanged.
- `sonar.typescript.lcov.reportPaths` in `sonar-project.properties` points to `coverage/lcov.info`.

**Rationale**: SonarCloud consumes lcov-formatted coverage data; adding the lcov reporter makes `coverage/lcov.info` available for the scanner without changing what is measured (100% coverage thresholds retained).

**Alternatives considered**:

- Use only SonarCloud's own TypeScript coverage — rejected: SonarCloud benefits from the lcov report produced by vitest's v8 provider; keeping vitest as the source of truth avoids diverging coverage configurations.

## Decision: Property sync with vitest configuration

**Decision**:

- `sonar.sources` = `src` matches vitest coverage `include: ['src/**/*.ts']`.
- `sonar.tests` = `tests/unit` matches vitest test `include: ['tests/**/*.test.ts', 'tests/**/*.spec.ts']`.
- `sonar.exclusions` mirrors vitest coverage `exclude` (`dist/`, `node_modules/`, `src/presentation/main.ts`, `src/**/*.d.ts`, `src/**/ports/**`, `src/**/*.type.ts`).
- `sonar.test.inclusions` mirrors vitest test `include` patterns.

**Rationale**: Satisfies FR-003/FR-004 and SC-003 — Sonar properties stay in sync with the project's configured source code locations and unit test inclusions/exclusions.

**Alternatives considered**:

- Duplicate path lists in both files without linking them — rejected: risks drift between vitest and Sonar configurations; keeping them aligned manually (documented) is the lightweight alternative.

## Decision: No acceptance tests

**Decision**: Per the spec, no acceptance tests (Cucumber/Gherkin) are implemented or automatically run by the agent. The existing acceptance scenarios remain unmodified (no functional change), per spec FR-005/SC-004. The agent does not execute Cucumber or CI.

**Rationale**: The spec explicitly states acceptance tests won't change and none are to be implemented or automatically run.
